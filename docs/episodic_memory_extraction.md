# Руководство по извлечению эпизодических знаний

Документ описывает, как мы превращаем сырую историю диалога в точные знания внутри стека Memory-Agents.

## 1. Источники данных

- **Рабочая память (Redis)** хранит полную историю промта по сессии (`agent:{agent_id}:session:{session_id}:messages`). Агенты читают окна сообщений через `get_messages` или `get_context`.
- **Эпизодическая память (MongoDB + Qdrant)** содержит подготовленные эпизоды, созданные через `create_episode(...)`, с метаданными (ID агента/пользователя/сессии, область доступа, важность, удовлетворённость, теги) и, при необходимости, эмбеддингами.
- **Семантическая память / Факты** получают дистиллированные знания, которые ссылаются на эпизодические доказательства.

## 2. Конвейер извлечения

1. **Собираем окно диалога** из рабочей памяти (часто последние N ходов или весь поток для аудита).
2. **Классифицируем сегменты** эвристиками или LLM, чтобы выделить:
   - события с сильным сигналом (достижение цели, эскалация, смена настроения);
   - устойчивые факты или предпочтения пользователя;
   - процедурные шаги, которые стоит формализовать.
3. **Создаём структурированные артефакты**:
   - эпизоды через `EpisodicMemoryService.create_episode` (траектория, итог, важность, теги, эмбеддинг);
   - факты через `FactsService.store_fact` для долговечных пользовательских атрибутов;
   - знания через `SemanticMemoryService.create_knowledge`, заполняя `supporting_evidence` ID эпизодов-доказательств.
4. **Опциональный семантический поиск**: при чтении `query_episodes` сначала применяет Mongo-фильтры (агент/пользователь/область/теги/временной промежуток/важность), затем передаёт отфильтрованный набор в Qdrant для поиска по эмбеддингам (`semantic_query`, `embedding`).
5. **Сбор контекста**: `retrieve_comprehensive_context` объединяет рабочую, эпизодическую, семантическую память и факты в единый пакет для RAG или планирования.

## 3. Стратегия точного извлечения

- **Гейтинг по метаданным**: область доступа, ID агент/пользователь, теги, временные фильтры и `min_importance` сокращают кандидатов до векторного поиска.
- **Векторный ранг**: заранее посчитанные эмбеддинги эпизодов позволяют сопоставлять по содержанию, а не только по метаданным.
- **Сортировка с учётом важности**: результаты упорядочиваются по `sort_by`/`sort_order`, обычно отдавая приоритет свежим, успешным и высокоценным эпизодам.
- **Доступ к траекториям**: `include_trajectory=True` возвращает пошаговый контекст, чтобы downstream-компоненты могли цитировать оригинальный диалог.
- **Дистилляция знаний**: после получения эпизода агент может превратить его в семантическое знание или процедурное обновление, гарантируя, что в долгосрочных хранилищах остаются только поддержанные фактами данные.

## 4. Рабочая память vs. долгосрочные хранилища

- Рабочая память хранит *всю* историю промта, но быстро истекает и служит буфером для извлечения.
- Долгосрочные хранилища (эпизоды, семантика, факты) содержат только данные, прошедшие фильтрацию, что предотвращает накопление шума.
- Агент может переобрабатывать рабочую память на лету (каждые несколько ходов), чтобы фиксировать новые факты до завершения сессии.

## 5. Поток памяти между слоями

| Этап | Триггер | Действие | Память назначения |
| --- | --- | --- | --- |
| **Оперативный буфер** | Входящие сообщения в живой сессии | `WorkingMemoryService.store_session` / `append_message` записывает диалог в Redis | **Рабочая память** хранит сырой контекст и временные переменные |
| **Формирование эпизода** | Эвристика/LLM находит значимое событие | Агент собирает контекст + траекторию и вызывает `create_episode(...)` | **Эпизодическая память** получает структурированный опыт с таймстемпом и эмбеддингом |
| **Дистилляция знаний** | Эпизод содержит полезный факт/процедуру | Агент вызывает `create_knowledge(...)` или `facts.store_fact(...)`, передавая `supporting_evidence` | **Семантическая память / Факты** фиксируют обобщённые инсайты с происхождением |
| **Процедуризация** | Траектория повторяемая | `procedural.store_procedure(...)` сохраняет код/шаги, ссылаясь на эпизод | **Процедурная память** копит исполнимые навыки |
| **Сбор контекста** | Другому агенту нужен свежий контекст | `retrieve_comprehensive_context(...)` подтягивает рабочее состояние + лучшие эпизоды + знания/факты | Аггрегированный пакет возвращается в промт, замыкая цикл |

Так данные «поднимаются» от шумной рабочей памяти к курируемым эпизодам и далее к дистиллированным семантическим/процедурным артефактам. Извлечение идёт в обратном порядке: сначала семантика/факты для кратких ответов, затем эпизоды для доказательств и, при необходимости, рабочая память для свежего контекста.

## 6. Точки входа API

| Цель | API | Примечание |
| --- | --- | --- |
| История чата | `WorkingMemoryService.get_messages` / `get_context` | Поток последних сообщений для анализа |
| Создать эпизод | `EpisodicMemoryService.create_episode` | Требует контекст, область, траекторию; поддерживает эмбеддинги и политики хранения |
| Получить эпизоды | `EpisodicMemoryService.query_episodes` | Сочетает Mongo-фильтры и сходство в Qdrant (`semantic_query`, `embedding`) |
| Сохранить знание | `SemanticMemoryService.create_knowledge` | Принимает `supporting_evidence`, чтобы связать знание с эпизодами |
| Сохранить факт | `FactsService.store_fact` | Версионирует пользовательские профили |
| Собрать контекст | `MemoryFacade.retrieve_comprehensive_context` | Возвращает выбранные эпизоды, знания, факты и рабочее состояние |

## 7. Эксплуатационные рекомендации

- По возможности используйте идемпотентные ключи, чтобы избегать дублей при ретраях.
- Настраивайте порог `importance`, балансируя полноту и точность; в хранилище должны попадать только ценные записи.
- Обеспечивайте一致ие эмбеддингов при записи и чтении эпизодов, чтобы сохранялась точность векторного поиска.
- Всегда логируйте `supporting_evidence`, чтобы аудит мог проследить происхождение знаний.

## 8. План развития

- Автоматизированные пайплайны суммаризации, переводящие траектории эпизодов в семантические знания без ручных промтов.
- Динамические (обучаемые) эвристики, которые решают, какие части истории стоит отправлять в эпизоды или семантику.
- Расширенные метаданные происхождения (оценка доверия, аннотаторы) для `supporting_evidence`.
