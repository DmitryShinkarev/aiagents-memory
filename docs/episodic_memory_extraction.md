# Извлечение точных знаний из эпизодической памяти

Этот документ описывает процесс превращения сырой истории диалога в структурированные знания с помощью системы Memory-Agents: от рабочей памяти до эпизодов и дистиллированных фактов.

---

## 1. Источники данных

### 1.1 Рабочая память (Redis)

**Назначение**: Временное хранилище всей истории диалога в активной сессии.

**Структура**: 
- Ключи вида `agent:{agent_id}:session:{session_id}:messages`
- Тип данных: Redis Streams для сообщений
- TTL: Настраивается (по умолчанию 1-24 часа)

**Методы доступа**:
- `get_messages(session_id)` — получить поток сообщений
- `get_context(agent_id, session_id)` — получить контекст сессии

**Характеристики**:
- Хранит **все** сообщения без фильтрации
- Быстрое чтение/запись (< 5ms)
- Автоматическое истечение по TTL
- Служит **буфером** для последующего анализа

### 1.2 Эпизодическая память (MongoDB + Qdrant)

**Назначение**: Долгосрочное хранение значимых событий и взаимодействий.

**Компоненты**:
- **MongoDB**: Документы с метаданными, траекториями, результатами
- **Qdrant**: Векторные индексы для семантического поиска

**Создание**: `EpisodicMemoryService.create_episode(...)`

**Метаданные эпизода**:
- `episode_id` — уникальный идентификатор
- `context` — {user_id, agent_id, session_id, team_id}
- `scope` — область доступа (user_private, team_shared и т.д.)
- `trajectory` — пошаговая последовательность действий
- `importance` — важность (0.0-1.0)
- `user_satisfaction` — удовлетворённость пользователя (опционально)
- `tags` — теги для категоризации
- `embedding` — векторное представление эпизода

### 1.3 Семантическая память и факты

**Назначение**: Обобщённые знания, извлечённые из эпизодов.

**Типы**:
- **Семантическая память**: Общие знания с temporal decay
- **Факты**: Конкретные пользовательские атрибуты

**Связь с эпизодами**: Поле `supporting_evidence` содержит ID эпизодов-доказательств.

## 2. Конвейер извлечения знаний

### 2.1 Сбор сырых данных

**Шаг 1**: Чтение окна диалога из рабочей памяти

```python
# Получить последние N сообщений
messages = await memory.working.get_messages(session_id, limit=50)

# Или полный контекст сессии
context = await memory.working.get_context(agent_id, session_id)
```

**Варианты окна**:
- Последние N ходов (для real-time анализа)
- Весь поток с начала сессии (для полного аудита)
- Скользящее окно с перекрытием (для continuous extraction)

### 2.2 Классификация и сегментация

**Шаг 2**: Анализ сообщений для выделения значимых событий

**Эвристики**:
- Ключевые слова: "проблема решена", "спасибо", "не помогло"
- Смена тональности (sentiment analysis)
- Завершение задачи (goal completion)
- Эскалация или ошибка

**LLM-классификация**:
```python
# Промпт для LLM
analysis_prompt = f"""
Проанализируй диалог и выдели:
1. Значимые события (цель достигнута, проблема возникла)
2. Факты о пользователе (предпочтения, личная информация)
3. Процедурные шаги, которые стоит сохранить

Диалог:
{messages}
"""
```

**Результат**: Список кандидатов на сохранение с типом (эпизод/факт/процедура).

### 2.3 Создание структурированных артефактов

**Шаг 3A**: Формирование эпизода

```python
await memory.create_episode(
    episode_id="ep_001",
    context=EpisodeContext(
        user_id="user_123",
        agent_id="support_agent",
        session_id="session_007"
    ),
    scope="user_private",
    episode_type="interaction",
    title="Решение биллинговой проблемы",
    trajectory=[
        {"step_id": "1", "role": "user", "content": "У меня двойное списание"},
        {"step_id": "2", "role": "agent", "action": "check_account"},
        {"step_id": "3", "role": "agent", "action": "process_refund"}
    ],
    outcome="Возврат средств обработан",
    importance=0.85,
    user_satisfaction=0.9,
    tags=["billing", "refund", "resolved"]
)
```

**Шаг 3B**: Извлечение фактов

```python
await memory.facts.store_fact(
    fact_id="fact_001",
    user_id="user_123",
    fact_type="preference",
    key="communication_channel",
    value="email",
    confidence=0.9,
    source="observed",
    evidence=["ep_001"]  # Ссылка на эпизод
)
```

**Шаг 3C**: Дистилляция знаний

```python
await memory.create_knowledge(
    knowledge_id="kb_001",
    knowledge="Премиум-пользователи имеют приоритет в обработке возвратов",
    source="inferred",
    confidence=0.85,
    agent_id="support_agent",
    supporting_evidence=["ep_001", "ep_002"],
    tags=["billing", "premium"]
)
```

### 2.4 Векторизация

**Шаг 4**: Создание эмбеддингов для семантического поиска

```python
# При создании эпизода
episode_text = f"{title} {outcome} {' '.join([step['content'] for step in trajectory])}"
embedding = await get_embedding(episode_text)  # OpenAI, Cohere и т.д.

await memory.create_episode(..., embedding=embedding)
```

## 3. Стратегия точного извлечения

### 3.1 Многоуровневая фильтрация

**Уровень 1: Метаданные (MongoDB)**

Фильтры до векторного поиска:
- `filter_by_user_id` — только эпизоды конкретного пользователя
- `filter_by_agent_id` — только эпизоды конкретного агента
- `filter_by_scope` — область доступа
- `filter_by_tags` — теги (например, ["billing"])
- `time_range_start/end` — временной промежуток
- `min_importance` — порог важности (например, ≥ 0.7)
- `only_successful` — только успешные эпизоды

**Преимущества**:
- Быстрая фильтрация по индексам MongoDB
- Гарантия соблюдения access control
- Уменьшение пространства поиска для Qdrant

**Уровень 2: Векторный поиск (Qdrant)**

После фильтрации метаданных:

```python
episodes = await memory.query_episodes(
    filter_by_user_id="user_123",
    filter_by_tags=["billing"],
    min_importance=0.7,
    semantic_query="проблемы с возвратом средств",  # Qdrant поиск
    limit=10
)
```

**Процесс**:
1. Запрос преобразуется в эмбеддинг
2. Qdrant ищет top-k похожих эпизодов **среди отфильтрованных**
3. Результаты ранжируются по косинусной близости

### 3.2 Сортировка и ранжирование

**Комбинированный скоринг**:

```
final_score = α × vector_similarity + β × importance + γ × recency
```

Где:
- `vector_similarity` — косинусная близость (0-1)
- `importance` — важность эпизода (0-1)
- `recency` — нормализованная свежесть (0-1)
- α, β, γ — веса (по умолчанию 0.6, 0.3, 0.1)

**Настройки сортировки**:

```python
episodes = await memory.query_episodes(
    ...,
    sort_by="importance",  # или "created_at", "user_satisfaction"
    sort_order="desc",
    limit=10
)
```

### 3.3 Доступ к траекториям

**Получение полного контекста**:

```python
episode = await memory.episodic.get_episode(
    episode_id="ep_001",
    include_trajectory=True  # Вернуть все шаги
)

# episode['trajectory'] содержит детальную последовательность
for step in episode['trajectory']:
    print(f"{step['role']}: {step['content']}")
```

**Использование**:
- Цитирование оригинального диалога в ответе
- Few-shot learning (примеры для промпта)
- Анализ паттернов взаимодействия

## 4. Рабочая память vs. долгосрочные хранилища

| Характеристика | Рабочая память | Эпизодическая память | Семантическая/Факты |
|----------------|----------------|----------------------|---------------------|
| **Полнота** | Весь промт | Только значимые события | Обобщённые знания |
| **TTL** | Часы/дни | Месяцы/годы | Бессрочно |
| **Фильтрация** | Нет | По важности | По релевантности |
| **Скорость доступа** | < 5ms | < 50ms | < 100ms (с векторами) |
| **Назначение** | Буфер | Исторический контекст | Факты и правила |

**Стратегия**:
- Храним всё в рабочей памяти → извлекаем ценное в эпизоды → дистиллируем в знания
- Избегаем дублирования: одно и то же не должно быть и эпизодом, и фактом (или чёткое разделение)
- Переобработка: агент может периодически (каждые 5-10 сообщений) анализировать рабочую память и создавать новые артефакты

## 5. Поток памяти между слоями

| Этап | Триггер | Действие | Память назначения |
| --- | --- | --- | --- |
| **Оперативный буфер** | Входящие сообщения | `WorkingMemoryService.store_session` / `append_message` | **Рабочая память** (Redis) |
| **Формирование эпизода** | Эвристика/LLM находит событие | `create_episode(...)` с контекстом и траекторией | **Эпизодическая память** (MongoDB + Qdrant) |
| **Дистилляция знаний** | Эпизод содержит факт | `create_knowledge(...)` или `facts.store_fact(...)` | **Семантическая память / Факты** |
| **Процедуризация** | Траектория повторяемая | `procedural.store_procedure(...)` | **Процедурная память** |
| **Сбор контекста** | Агенту нужен контекст | `retrieve_comprehensive_context(...)` | Аггрегированный пакет |

**Направления потока**:
- **Вверх**: Рабочая → Эпизодическая → Семантическая/Процедурная (от сырых данных к обобщённым)
- **Вниз**: Семантика/Факты → Эпизоды → Рабочая (при извлечении контекста для промпта)

## 6. API точки входа

| Цель | API | Примечание |
| --- | --- | --- |
| История чата | `WorkingMemoryService.get_messages` / `get_context` | Поток последних сообщений |
| Создать эпизод | `EpisodicMemoryService.create_episode` | Требует контекст, траекторию, embedding |
| Получить эпизоды | `EpisodicMemoryService.query_episodes` | Mongo-фильтры + Qdrant similarity |
| Сохранить знание | `SemanticMemoryService.create_knowledge` | Принимает `supporting_evidence` |
| Сохранить факт | `FactsService.store_fact` | Версионирование профилей |
| Собрать контекст | `MemoryFacade.retrieve_comprehensive_context` | Объединяет все типы памяти |

## 7. Эксплуатационные рекомендации

### 7.1 Идемпотентность

Используйте `idempotency_key` при создании эпизодов, чтобы избежать дублей при ретраях:

```python
await memory.create_episode(
    episode_id="ep_001",
    idempotency_key="create_ep_001_user_123",
    ...
)
```

### 7.2 Пороги важности

Настраивайте `importance` для балансировки полноты и точности:

- **importance ≥ 0.8**: Критически важные события (успешные решения, эскалации)
- **importance ≥ 0.5**: Обычные взаимодействия
- **importance < 0.5**: Второстепенная информация (может быть отфильтрована)

### 7.3 Консистентность эмбеддингов

Используйте **одну и ту же модель** для создания и поиска эмбеддингов:

```python
# При создании
embedding = await openai_embed(text)

# При поиске
query_embedding = await openai_embed(query)  # Та же модель!
```

### 7.4 Трассировка происхождения

Всегда указывайте `supporting_evidence` при создании знаний:

```python
await memory.create_knowledge(
    ...,
    supporting_evidence=["ep_001", "ep_002"],  # Трейсбек к эпизодам
    ...
)
```

## 9. План развития

### 9.1 Автоматизация

- **Автоматические пайплайны суммаризации**: Эпизодная траектория → семантическое знание без ручных промптов
- **Continuous extraction**: Фоновый процесс, который непрерывно анализирует рабочую память

### 9.2 Обучаемые эвристики

- **ML-модели для классификации**: Обучение на размеченных эпизодах для автоматического определения важности
- **Адаптивные пороги**: Динамическая настройка `min_importance` на основе feedback

### 9.3 Расширенная трассировка

- **Confidence scores**: Оценка достоверности для каждого `supporting_evidence`
- **Annotator info**: Кто/что извлекло знание (человек, LLM, эвристика)
- **Version control**: История изменений знаний с ссылками на источники

### 9.4 Мультимодальность

- Поддержка изображений, аудио, видео в траекториях эпизодов
- Векторизация мультимодального контента

## Резюме

**Процесс извлечения знаний**:

1. **Рабочая память** собирает всю историю диалога без фильтрации
2. **Анализ** (эвристики/LLM) выделяет значимые события, факты, процедуры
3. **Эпизодическая память** сохраняет структурированные события с метаданными и эмбеддингами
4. **Семантическая память / Факты** хранят дистиллированные знания со ссылками на эпизоды
5. **Извлечение** через многоуровневую фильтрацию (метаданные → векторный поиск) даёт точные результаты

**Ключевые принципы**:
- Храните всё → фильтруйте важное → дистиллируйте знания
- Используйте метаданные для быстрой фильтрации, векторы для семантической точности
- Поддерживайте трассировку через `supporting_evidence`
- Балансируйте real-time и batch-обработку в зависимости от требований
